# 第三阶段实施方案：V2 发布检查与正式发布

> 目标版本：`v2.0.0`
> 起始基线：提交 `a090163` / `v2.0.0-rc.3`
> 阶段性质：发布工程与兼容性验证，不新增产品功能。

## 1. 目标与边界

本阶段关闭 `TEST.md` 中全部 P1 项，修复检查中发现的 P0/P1 缺陷，并在所有门禁通过后生成正式版本。重点验证真实用户路径，而不是继续扩功能。

本阶段不做：V2.4 功能、小程序、云同步、多币种、解析 PDF/XLSX、重写框架、引入线上服务。

## 2. 交付物

- 发布兼容性证据：桌面端、移动端、离线、Service Worker 升级、文件导出恢复、大数据量。
- 自动化补强：能稳定自动化的部分进入 `tests/`；依赖 Excel/Numbers 或真机的部分保留人工证据模板。
- 所有检查中发现的 P0/P1 缺陷及回归测试。
- 版本统一为 `v2.0.0` 的代码和文档。
- 发布提交与本地 annotated tag `v2.0.0`；未经用户授权不推送远端。

├── performance.test.js           # 确定性大数据生成与核心性能检查

## 3. 执行顺序与工作包

### P3.0 基线冻结

执行：

```bash
git status --short
node --test
node --check js/core.js
node --check js/db.js
node --check js/charts.js
node --check js/app.js
node --check sw.js
node --check tests/browser-harness.js
```

再从本地 HTTP 服务打开 `tests/browser-harness.html`，确认 9/9。把提交哈希、浏览器版本、操作系统、时间记录到人工检查表。基线若不是 `a090163`，先比对改动并在报告中写明新的起点。

完成门槛：Node 98/98、浏览器 9/9、工作区状态已记录。

### P3.1 文件导出与恢复闭环

实现/验证路径：

1. 在全新浏览器配置中新建 3 笔虚构交易，覆盖中文、逗号、双引号、转账和两位小数。
2. 点击“导出 JSON 备份”，确认文件真实落盘；记录文件名、字节数和 SHA-256。
3. 点击“导出 CSV 明细”，分别用 Excel 与 Numbers 打开；目视检查 UTF-8 中文、金额两位小数、含逗号/引号商户字段、日期列和转账账户列。
4. 清空应用后从刚下载的 JSON 文件恢复；核对交易数、账户、分类、设置和月度汇总。
5. 再次导出 JSON，去除 `exportedAt` 后做结构化深比较。数组顺序不同不得直接判失败，应按 `id` 排序后比较。

需要补代码时：导出/恢复的业务规则只能落在 `Core.createBackup`、`Core.restoreStateFromBackup`、`Core.transactionsToCSV`；`app.js` 只负责文件交互和提示。

验收标准：

- 下载文件可真实打开，CSV 无乱码或错列。
- 恢复前后财务汇总、记录 ID 和关联字段一致。
- 损坏 JSON、未来 Schema、错误 app 标识被拒绝，拒绝前原数据不变。
- 文件选择器取消不报错、不清空当前状态。

### P3.2 离线启动、离线写入与 Service Worker 升级

#### 离线业务验收

1. 在线首次访问应用，等待 Service Worker 激活并确认壳资源进入 Cache Storage。
2. 停止本地 HTTP 服务或在浏览器强制离线。
3. 完全关闭页面后重新打开同一 URL。
4. 离线新增、编辑、删除一笔虚构交易并刷新页面。
5. 核对 IndexedDB 持久化、首页汇总和统计页。

#### 旧版本升级验收

使用同一 origin 和同一端口验证真实升级，不能只改 Cache Storage：

1. 用临时 worktree 检出 `58f261a`，在固定端口安装 rc.1 Service Worker。
2. 关闭旧服务，用当前分支在相同端口启动服务。
3. 调用 `registration.update()` 或正常重访，等待 `controllerchange`。
4. 确认页面显示新版本、已有 IndexedDB 数据仍在、旧 `ledger-*` 缓存被删除。
5. 确认同 origin 下非 `ledger-` 前缀缓存未被误删。

代码审查重点：当前 `sw.js` 激活阶段不应删除其他应用缓存；清理条件应限制为“小账本缓存前缀且不是当前缓存”。缓存数组必须覆盖所有应用壳资源，失败时不得产生半可用缓存。

验收标准：在线首次加载、断网冷启动、断网 CRUD、旧版升级、旧缓存清理全部通过；无外域请求；业务数据不因 SW 更新丢失。

### P3.3 手机尺寸与交互检查

至少覆盖 320、375、390、430 CSS px 宽度，以及一台 iOS Safari/PWA 和一台 Android Chrome/PWA 真机或等价设备。逐项检查：

- 底部导航不被安全区遮挡；滚动到底后内容不被导航覆盖。
- 记账数字键盘、系统软键盘、底部弹层同时出现时仍可提交/关闭。
- 导入向导、筛选器、交易详情、应用锁在窄屏不横向溢出。
- 44px 左右的触控目标可用，不依赖 hover。
- 长账户名、长商户名、较大金额不会把操作按钮挤出屏幕。
- 横竖屏切换不丢表单草稿；若产品只支持竖屏，横屏要可用而不是崩溃。

修复只允许使用响应式 CSS 和现有原生交互，不引入 UI 框架。每个布局缺陷至少增加一个可重复的 DOM/截图检查记录。

### P3.4 大数据量与重复提交保护

在 `tests/fixtures/performance.js` 生成固定种子的 1,000、10,000、20,000 条虚构流水，覆盖 24 个月、四种来源、转账、退款、报销、周期账和合并关系。不得使用真实账单。

测试四条路径：

1. 解析 + `buildTxns` + `matchDuplicates`。
2. 聚合、12 月趋势、异常检测与订阅检测。
3. IndexedDB 保存、刷新加载、JSON 导出恢复。
4. 导入按钮双击/连续点击，最终只提交一次。

目标门槛（在测试报告记录设备，不把硬件差异隐藏掉）：

- 10,000 条核心导入管线目标不超过 5 秒；20,000 条不得崩溃或出现错误结果。
- 首页/明细/统计首次渲染目标不超过 2 秒；若超标，先做分页/分段渲染，不改变统计口径。
- 连续点击“确认导入”只产生一次持久化；用显式 `busy` 状态禁用按钮，保存成功或失败后正确释放。
- 任意规模下同源幂等、跨源候选唯一规则和金额汇总结果不变。

性能优化顺序：先测量，再用 `Map`/索引降低重复扫描，再做明细分页或分段渲染；不得先引入 Web Worker 或依赖库。若需 Web Worker，另写 ADR 说明序列化成本和离线缓存变更。

### P3.5 缺陷处理与全量回归

分级：

- P0：金额/方向/余额错误、数据丢失、加密绕过、真实隐私外联。立即停止发布，必须修复。
- P1：主要功能在目标浏览器不可用、离线失败、SW 升级卡死、恢复或导出失败、严重移动端阻断。必须修复。
- P2：不阻断主要流程的显示或易用性问题。可记录后进入 V2.0.1，但需用户确认。

每个 P0/P1 必须包含“失败 fixture/步骤 → 最小修复 → 专项回归 → 全量回归”。完成后运行 Node 全套、浏览器验收页、人工 P1 清单和静态资源检查。

### P3.6 正式版本与发布门禁

只有以下条件全部满足才执行版本切换：

- `TEST.md` 无未完成 P0/P1，所有 P1 有复现证据。
- Node 与浏览器验收全绿，JavaScript 语法、静态资源、敏感信息扫描通过。
- `git diff --check` 通过，工作区无无关变更。
- 用户确认可以从 RC 转正式版。

版本切换清单：

1. `js/app.js` 的 `APP_VERSION` 改为 `2.0.0`。
2. `sw.js` 的缓存键改为 `ledger-v2.0.0`，检查资源清单。
3. `README.md`、`STATUS.md`、`TEST.md`、`CHANGELOG.md` 从 RC 状态改为正式发布。
4. 把 CHANGELOG 的 Unreleased 内容移入 `[2.0.0] - YYYY-MM-DD`。
5. 再跑全部门禁，生成单独发布提交。
6. 创建 annotated tag `v2.0.0`。没有用户明确授权时不执行 `git push`、不发布网站。

建议提交粒度：

```text
test: cover v2 release compatibility gates
fix: resolve <具体 P1 缺陷>
docs: record v2 release evidence
release: v2.0.0
```

## 5. 回滚方案

- 代码问题：保留上一 RC 提交，不改写历史；以新提交修复或回退发布提交。
- SW 问题：发布修正版缓存键，不复用有问题的缓存名；确保 `activate` 仅清理 `ledger-*` 旧缓存。
- 数据问题：停止发布，先导出当前 JSON；通过修复后的迁移恢复。禁止建议用户清站点数据作为常规修复。
- 正式标签打错：不要强推覆盖公开标签；创建补丁版本。若标签仅本地且未分享，需用户确认后再处理。
